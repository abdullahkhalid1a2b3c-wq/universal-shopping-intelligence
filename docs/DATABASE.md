# FitSense Database Documentation

This document describes the Supabase PostgreSQL schema, data relationships, Row Level Security (RLS) policies, and database execution instructions for FitSense.

---

## 1. Table Summary & Relationships

All tables feature a primary key `id UUID DEFAULT gen_random_uuid()` and timestamp `created_at TIMESTAMPTZ DEFAULT NOW()`.

### Customer & Authentication
1. **`profiles`**
   - **Purpose:** User profile created automatically on auth sign-up via PostgreSQL trigger `on_auth_user_created`.
   - **Key Fields:** `user_id` (unique, FK to `auth.users`), `display_name`, `preferred_language` (`en`, `ur`, `ur-roman`), `preferred_unit` (`cm`, `in`), `gender_category`, `height_cm`, `weight_kg`, `role` (`customer`, `retailer`, `admin`).
2. **`consents`**
   - **Purpose:** Explicit GDPR/privacy consents recorded before collecting personal body measurements or analytics.
   - **Key Fields:** `user_id` (FK to `auth.users`), `consent_type` (`store_measurements`, `use_feedback_for_analytics`), `granted`, `granted_at`, `policy_version`.
3. **`body_measurements`**
   - **Purpose:** Core customer body measurements stored in centimetres with sanity range checks.
   - **Key Fields:** `user_id` (unique, FK to `auth.users`), `chest_cm` (50–200), `waist_cm` (40–180), `hip_cm` (50–200), `shoulder_cm` (25–70), `sleeve_cm` (20–100), `inseam_cm` (30–120), `thigh_cm` (25–100), `torso_length_cm` (30–100), `kameez_length_cm` (50–160).
4. **`fit_preferences`**
   - **Purpose:** Category-specific fit preferences (e.g. regular for shirts, fitted for t-shirts).
   - **Key Fields:** `user_id` (FK to `auth.users`), `category` (`tshirt_top`, `shirt`, `trouser`, `jeans`, `kurta`, `dress`), `fit` (`fitted`, `regular`, `loose`). Unique per `(user_id, category)`.
5. **`reference_garments`**
   - **Purpose:** Flat measurements of a customer's favorite existing garment for comparative sizing.
   - **Key Fields:** `user_id` (FK to `auth.users`), `category`, `label`, `measurements` (JSONB), `notes`.
6. **`saved_items`**
   - **Purpose:** User wishlist or saved sizing recommendations.
   - **Key Fields:** `user_id`, `product_id`, `size_label`, `status` (`saved`, `bought`, `dismissed`), `bought_at`.

### Retailer & Catalogue
7. **`retailers`**
   - **Purpose:** Brand / merchant entities.
   - **Key Fields:** `name`, `slug` (unique), `website_domain`, `logo_url`, `supports_cod`, `return_policy_url`, `status` (`pending`, `verified`, `suspended`).
8. **`retailer_members`**
   - **Purpose:** Access control mapping between users and retailers.
   - **Key Fields:** `retailer_id`, `user_id`, `member_role` (`owner`, `editor`). Unique per `(retailer_id, user_id)`.
9. **`size_charts`**
   - **Purpose:** Sizing charts belonging to retailers.
   - **Key Fields:** `retailer_id`, `name`, `category`, `gender_category`, `measured_as` (`flat`, `circumference`), `unit_source` (`cm`, `in`), `source_note`, `verified_at`, `verified_by`, `is_demo`.
10. **`size_chart_rows`**
    - **Purpose:** Individual size dimensions per chart row.
    - **Key Fields:** `size_chart_id`, `size_label` (e.g. 'S', 'M', '32'), `sort_order`, `measurement_key` (`chest`, `waist`, `hip`, `shoulder`, `sleeve`, `length`, `inseam`, `thigh`, `rise`, `hem`), `value_cm`. Unique per `(size_chart_id, size_label, measurement_key)`.
11. **`products`**
    - **Purpose:** Garment catalogue items.
    - **Key Fields:** `retailer_id`, `name`, `category`, `gender_category`, `product_url`, `canonical_url` (unique), `external_id`, `size_chart_id`, `fabric`, `stretch_pct` (0–40), `thickness`, `transparency`, `shrinkage_pct`, `season`, `is_active`, `is_demo`, `fit_cut`.

### Recommendations, Feedback & Store Adapters
12. **`recommendations`**
    - **Purpose:** History of fit recommendations generated by the fit engine.
    - **Key Fields:** `user_id` (nullable for guest lookups), `product_id`, `recommended_size`, `confidence_score` (0–100), `confidence_label`, `inputs_snapshot` (JSONB; measurements omitted unless consent is granted).
13. **`fit_feedback`**
    - **Purpose:** Post-purchase feedback loop to validate sizing accuracy.
    - **Key Fields:** `user_id`, `product_id`, `size_bought`, `fit_result` (`too_tight`, `slightly_tight`, `perfect`, `slightly_loose`, `too_loose`), `problem_area`, `was_returned`, `note`, `body_snapshot` (JSONB, only if consent granted). Unique per `(user_id, product_id, size_bought)`.
14. **`store_adapters`**
    - **Purpose:** Browser extension DOM scraping configuration per brand website.
    - **Key Fields:** `domain` (unique), `platform` (`shopify`, `woocommerce`, `custom`), `selectors` (JSONB), `is_enabled`.
15. **`coverage_requests`**
    - **Purpose:** Customer requests to add unsupported fashion stores.
    - **Key Fields:** `user_id` (nullable), `page_url`, `domain`.

## 2. Row Level Security (RLS) in Plain English

Every single table in FitSense has PostgreSQL Row Level Security enabled:

1. **Customer Privacy:**
   - A customer can only view, insert, update, or delete their own rows in `profiles`, `consents`, `body_measurements`, `fit_preferences`, `reference_garments`, `saved_items`, `recommendations`, and `fit_feedback`.
   - Other users, including retailers, cannot query customer body measurements.
2. **Retailers:**
   - Anyone (even guests) can browse retailers whose status is `verified`.
   - Retailer members can view and update their own retailer profile.
   - Any signed-in user can register a new retailer (which defaults to `pending` status until admin review) and automatically becomes its `owner`.
3. **Catalogue & Size Charts:**
   - Any shopper can view size charts, size chart rows, and products if the retailer is `verified` or if `is_demo = true`.
   - Only authorized members of the retailer (or admins) can create, modify, or delete products and size charts for that retailer.
4. **Store Adapters:**
   - Publicly readable only when `is_enabled = true`. Modifications are restricted to admins.
5. **Coverage Requests:**
   - Any authenticated shopper can submit an unsupported retailer URL. Only admins can view requests.
6. **Analytics Views:**
   - Defined with `WITH (security_invoker = true)` to inherit calling user permissions. Retailers can only view aggregated data for products they own.

## 3. Localized Explanations (Urdu & Roman Urdu)

Recommendation explanations are localized across three language variants:
- English (`en`)
- Urdu (`ur`, right-to-left)
- Roman Urdu (`ur-roman`, left-to-right)

> **Localization Review Note:** The Urdu and Roman Urdu translation template strings in `apps/api/app/fit/i18n/ur.json` and `apps/api/app/fit/i18n/ur-roman.json` are initial working copies. A native Urdu speaker must review them before production pilot deployment to ensure cultural resonance and authentic phrasing.

## 4. Database Migration & Execution Instructions

Follow these exact steps in your Supabase project:

1. **Open Supabase Dashboard:**
   - Navigate to [https://supabase.com/dashboard](https://supabase.com/dashboard) and select your project.
2. **Open SQL Editor:**
   - In the left sidebar, click on the **SQL Editor** icon.
3. **Run Migration Files in Order:**
   - Create a new query, paste the contents of `supabase/migrations/00001_initial_schema.sql`, and click **Run**.
   - Create a new query, paste the contents of `supabase/migrations/00002_rls_and_policies.sql`, and click **Run**.
   - Create a new query, paste the contents of `supabase/migrations/00003_analytics_and_storage.sql`, and click **Run**.
4. **Run Seed Data:**
   - Create a new query, paste the contents of `supabase/seed.sql`, and click **Run**.
5. **Enable Email Auth:**
   - Go to **Authentication** -> **Providers** -> **Email** and ensure email signup/login is enabled.
6. **Copy Credentials to `.env`:**
   - Go to **Project Settings** -> **API**.
   - Copy **Project URL** -> `NUXT_PUBLIC_SUPABASE_URL`, `SUPABASE_URL`, `VITE_SUPABASE_URL`.
   - Copy **anon / public key** -> `NUXT_PUBLIC_SUPABASE_KEY`, `VITE_SUPABASE_KEY`.
   - Copy **service_role key** -> `SUPABASE_SERVICE_KEY` in `apps/api/.env`.
   - Copy **JWT Secret** -> `SUPABASE_JWT_SECRET` in `apps/api/.env`.
